# C 语言国密工具库 (crossmool-c) 需求规格说明书

## 1. 引言

### 1.1 功能概述
本项目旨在基于 GmSSL 库开发一套 C 语言实现的国密算法工具库，包含 SM2（非对称加密/签名）、SM3（杂凑算法）、SM4（对称加密）三种算法的实用工具方法。该库需要与已有的 Java 版本实现完全互通，支持相同的签名格式、杂凑算法和密文格式（C1C3C2）。

### 1.2 背景与目标
- **背景**：crossmool 项目已在 Java、C++、C#、Go、JavaScript、Python、Rust 等多个语言平台实现了国密算法工具库，现需补充 C 语言版本
- **目标**：提供一个易于被其他 C 语言应用系统引用的程序依赖包，支持 C20 标准及以上版本，兼容 GCC、Clang/LLVM、MSVC 三大编译器
- **互通性**：确保与 Java 版本的完全互通，使用相同的密钥格式、加密格式、签名格式

### 1.3 关键利益相关者与用户
- **目标用户**：需要使用国密算法的 C 语言开发者
- **集成场景**：嵌入式系统、网络应用、安全模块等 C 语言项目
- **维护团队**：crossmool 项目维护者

### 1.4 预期价值与收益
- 提供原生 C 语言的国密算法实现
- 支持多种编码格式（byte[]、Base64、HEX）
- 易于集成到现有 C 语言项目
- 与多语言版本保持互通性

## 2. 需求

### 2.1 用户管理

#### 需求 1：密钥对生成

**用户故事**：作为一名 C 语言开发者，我希望能够生成 SM2 密钥对，以便进行加密和签名操作。

**验收标准（EARS 格式）**：

1. 当调用 `sm2_generate_keypair()` 时，系统应生成符合 SM2 标准的密钥对
2. 如果调用 `sm2_generate_keypair_base64()`，则系统应返回 Base64 编码的公钥和私钥字符串
3. 如果调用 `sm2_generate_keypair_hex()`，则系统应返回 HEX 编码的公钥和私钥字符串
4. 系统应支持 ASN.1/X.509 格式的密钥导出（公钥以"30"开头，私钥为 PKCS8 格式）
5. 当内存分配失败时，系统应返回错误码并释放已分配的资源

### 2.2 核心功能

#### 需求 2：SM2 加密解密

**用户故事**：作为一名 C 语言开发者，我希望使用 SM2 算法对数据进行加密和解密，以便保护数据的安全性。

**验收标准（EARS 格式）**：

1. 当调用 `sm2_encrypt()` 时，系统应使用公钥对数据进行加密，返回 C1C3C2 格式的密文
2. 如果输入为 byte 数组，则系统应返回 byte 数组格式的密文
3. 如果调用 `sm2_encrypt_to_hex()`，则系统应返回 HEX 编码的密文字符串
4. 如果调用 `sm2_encrypt_to_base64()`，则系统应返回 Base64 编码的密文字符串
5. 当调用 `sm2_decrypt()` 时，系统应使用私钥对密文进行解密，返回原始数据
6. 如果密文为 HEX 或 Base64 字符串，则系统应自动识别并解码后进行解密
7. 当解密失败时，系统应返回错误码

#### 需求 3：SM2 签名验签

**用户故事**：作为一名 C 语言开发者，我希望使用 SM2 算法对数据进行签名和验签，以便验证数据的完整性和来源。

**验收标准（EARS 格式）**：

1. 当调用 `sm2_sign()` 时，系统应使用私钥对数据进行签名，返回 64 字节的签名数据
2. 如果调用 `sm2_sign_to_hex()`，则系统应返回 HEX 编码的签名字符串
3. 如果调用 `sm2_sign_to_base64()`，则系统应返回 Base64 编码的签名字符串
4. 当调用 `sm2_verify()` 时，系统应使用公钥验证签名的有效性
5. 如果签名验证通过，则系统应返回 1（true）
6. 如果签名验证失败，则系统应返回 0（false）
7. 系统应使用固定的 USER_ID ("1234567812345678") 进行签名和验签

#### 需求 4：SM3 杂凑

**用户故事**：作为一名 C 语言开发者，我希望使用 SM3 算法计算数据的杂凑值，以便验证数据的完整性。

**验收标准（EARS 格式）**：

1. 当调用 `sm3_digest()` 时，系统应计算输入数据的 SM3 杂凑值，返回 32 字节的杂凑结果
2. 如果调用 `sm3_digest_to_hex()`，则系统应返回 HEX 编码的杂凑值字符串
3. 如果调用 `sm3_digest_to_base64()`，则系统应返回 Base64 编码的杂凑值字符串
4. 当输入数据为空时，系统应返回错误码

#### 需求 5：SM3-HMAC

**用户故事**：作为一名 C 语言开发者，我希望使用 HMAC-SM3 算法计算消息认证码，以便验证消息的完整性和来源。

**验收标准（EARS 格式）**：

1. 当调用 `sm3_hmac()` 时，系统应使用密钥和数据计算 HMAC-SM3 值
2. 如果调用 `sm3_hmac_to_hex()`，则系统应返回 HEX 编码的 HMAC 值字符串
3. 如果调用 `sm3_hmac_to_base64()`，则系统应返回 Base64 编码的 HMAC 值字符串
4. 当调用 `sm3_hmac_verify()` 时，系统应验证接收到的 HMAC 值是否有效
5. 如果密钥长度小于 32 字节，则系统应返回错误码

#### 需求 6：SM4 对称加密

**用户故事**：作为一名 C 语言开发者，我希望使用 SM4 算法对数据进行对称加密和解密，以便高效地保护数据。

**验收标准（EARS 格式）**：

1. 当调用 `sm4_generate_key()` 时，系统应生成 16 字节的随机密钥
2. 如果调用 `sm4_encrypt_ecb()`，则系统应使用 ECB 模式和 PKCS7 填充对数据进行加密
3. 如果调用 `sm4_decrypt_ecb()`，则系统应对密文进行解密，返回原始数据
4. 当密钥长度不为 16 字节时，系统应返回错误码
5. 系统应返回 HEX 编码的密文字符串

#### 需求 7：加密签名组合操作

**用户故事**：作为一名 C 语言开发者，我希望能够一次性完成加密和签名操作，以便简化业务流程。

**验收标准（EARS 格式）**：

1. 当调用 `sm2_encrypt_sign()` 时，系统应先加密数据再对密文签名，返回密文和签名的组合
2. 如果调用 `sm2_verify_decrypt()`，则系统应先验签再解密，返回原始数据
3. 如果验签失败，则系统应返回错误码并不进行解密

### 2.3 数据管理

#### 需求 8：字符集支持

**用户故事**：作为一名 C 语言开发者，我希望工具库支持多种字符集，以便处理不同编码的文本数据。

**验收标准（EARS 格式）**：

1. 当未指定字符集时，系统应默认使用 UTF-8 编码
2. 如果指定了其他字符集（如 GBK、ISO-8859-1），则系统应使用指定的字符集进行编码转换
3. 当字符集不支持时，系统应返回错误码

#### 需求 9：编码格式支持

**用户故事**：作为一名 C 语言开发者，我希望工具库支持 byte 数组、Base64、HEX 三种编码格式，以便灵活地处理数据。

**验收标准（EARS 格式）**：

1. 当输入为 HEX 字符串时，系统应自动识别并解码为 byte 数组
2. 如果输入为 Base64 字符串，则系统应自动识别并解码为 byte 数组
3. 系统应提供 `is_hex_string()` 和 `is_base64_string()` 函数用于格式检测
4. 系统应提供 `hex_encode()`、`hex_decode()`、`base64_encode()`、`base64_decode()` 工具函数

### 2.4 API / 集成

#### 需求 10：C 语言 API 设计

**用户故事**：作为一名 C 语言开发者，我希望工具库提供简洁、清晰的 C 语言 API，以便易于集成到现有项目中。

**验收标准（EARS 格式）**：

1. 当调用任何 API 函数时，系统应返回 int 类型的状态码（0 表示成功，负数表示错误）
2. 如果输出参数为指针类型，则系统应通过指针返回结果数据
3. 系统应提供 `crossmool_error_string()` 函数用于获取错误描述
4. 系统应提供 `crossmool_version()` 函数用于获取库版本号

#### 需求 11：内存管理

**用户故事**：作为一名 C 语言开发者，我希望工具库提供明确的内存管理接口，以便避免内存泄漏。

**验收标准（EARS 格式）**：

1. 当 API 函数返回动态分配的内存时，系统应提供对应的 `free()` 函数用于释放内存
2. 如果调用失败，系统应自动释放已分配的临时内存
3. 系统应提供 `crossmool_cleanup()` 函数用于清理全局资源

### 2.5 安全

#### 需求 12：输入验证

**用户故事**：作为一名 C 语言开发者，我希望工具库对所有输入参数进行严格验证，以防止安全漏洞。

**验收标准（EARS 格式）**：

1. 当输入参数为 NULL 时，系统应返回错误码
2. 如果密钥格式不正确，则系统应返回错误码
3. 当数据长度超过限制时，系统应返回错误码
4. 系统应对所有字符串输入进行边界检查

#### 需求 13：密钥保护

**用户故事**：作为一名 C 语言开发者，我希望工具库能够安全地处理密钥数据，以防止密钥泄露。

**验收标准（EARS 格式）**：

1. 当密钥使用完毕后，系统应安全地清除内存中的密钥数据
2. 系统不应将密钥写入日志或临时文件
3. 系统应使用安全的内存分配函数（如 `mlock()`）保护敏感数据

### 2.6 性能

#### 需求 14：性能优化

**用户故事**：作为一名 C 语言开发者，我希望工具库具有良好的性能表现，以便满足实时性要求。

**验收标准（EARS 格式）**：

1. 当处理大数据量时，系统应使用高效的内存操作函数
2. 系统应避免不必要的内存拷贝
3. 系统应支持批量处理操作

### 2.7 错误处理

#### 需求 15：错误码定义

**用户故事**：作为一名 C 语言开发者，我希望工具库提供清晰的错误码定义，以便快速定位问题。

**验收标准（EARS 格式）**：

1. 当操作成功时，系统应返回 0
2. 如果发生参数错误，则系统应返回 -1
3. 如果发生内存分配失败，则系统应返回 -2
4. 如果发生加密/解密失败，则系统应返回 -3
5. 如果发生签名/验签失败，则系统应返回 -4
6. 如果发生格式转换错误，则系统应返回 -5

### 2.8 用户体验

#### 需求 16：文档和示例

**用户故事**：作为一名 C 语言开发者，我希望工具库提供完善的文档和示例代码，以便快速上手。

**验收标准（EARS 格式）**：

1. 系统应提供 README.md 文档说明安装和使用方法
2. 系统应提供 API 参考文档说明每个函数的用法
3. 系统应提供示例代码展示常见使用场景
4. 系统应提供与 Java 版本的互通性测试代码

#### 需求 17：构建和部署

**用户故事**：作为一名 C 语言开发者，我希望工具库易于构建和部署，以便快速集成到项目中。

**验收标准（EARS 格式）**：

1. 当使用 CMake 构建时，系统应支持静态库和动态库两种模式
2. 系统应支持使用 vcpkg 安装 GmSSL 依赖
3. 系统应提供 crossmool-config.cmake 文件便于其他项目集成
4. 系统应生成头文件、库文件和导入库文件

## 3. 非功能性需求

### 3.1 兼容性

- 支持 C20 标准及以上版本
- 兼容 GCC 7.0+、Clang/LLVM 10.0+、MSVC 2019+
- 支持 Windows、Linux、macOS 平台

### 3.2 可维护性

- 代码结构清晰，注释完整
- 遵循 C 语言最佳实践
- 提供单元测试覆盖核心功能

### 3.3 可扩展性

- 模块化设计，便于后续扩展新算法
- 预留扩展接口，支持未来功能增强
